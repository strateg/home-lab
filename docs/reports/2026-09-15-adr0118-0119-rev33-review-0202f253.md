# ADR 0118/0119 rev 3.3 — architecture review

Date: 2026-09-15. Reviewed revision: `0202f253` (clean before this report).
Scope: the amendment's five changed documents, existing capability/architecture
contracts and the proposed next implementation step. No production implementation
or ADR status changed by this review. Full tests, compilation and parity were not
rerun; this is design review with one scoped executable counterexample.

## Verdict

Keep the distinction between runtime target, enforcer type, enforcer instance and
policy plane. Keep capability-driven classification separate from SEC-CAP proof.
Do not freeze the implementation seam yet: rev 3.3 still conflates enforcement
identity, scope cardinality, transport credentials and deployment/state ownership.

## R1 — P1: enforcer identity is not scope identity; the proposed index loses scopes

Locations: ADR0119 D1/D1.1, lines 64-76 and 99-110;
`topology-tools/plugins/compilers/security_matrix_compiler.py:118-151`.

M1-B says each matrix names one enforcer. It does NOT say an enforcer has only one
matrix/scope. D1's `scope = managed_by_ref` and D1.1's two instances -> two scopes
leave the reverse cardinality unstated. A perimeter and an internal scope on the
same device must remain distinguishable and have independently applicable rules.
The accepted design already permits multiple disjoint contexts on a device.

Executable counterexample at 0202f253: compile one trust zone and two matrices,
with distinct matrix IDs and planes but `managed_by_ref = rtr.shared`. Read the
published results using a scoped test consumer, not direct registry access.

| Input order | matrix_by_enforcer[rtr.shared] | Result |
|---|---|---|
| perimeter, internal | internal matrix ID | SUCCESS, no diagnostics |
| internal, perimeter | perimeter matrix ID | SUCCESS, no diagnostics |

Both matrices remain in `security_matrices`; the proposed lookup channel drops
one. Therefore subscribing to that channel and removing the generator's early
return does not establish completeness or determinism.

Required correction: define scope identity independently; declare one scope ->
one enforcer and one enforcer -> many scopes/contexts. Specify the matrix-index
contract as a complete collection (or explicitly reject unsupported multiplicity),
with deterministic ordering and cross-scope composition/ownership validation.
Plane separation is semantic, not proof that shared chains/resources are isolated.

## R2 — P1: logical separation is conflated with connection and state separation

Locations: ADR0119 D1.1 lines 99-107; W07 lines 108-119.

The normative statement demands one address, credential set and state per enforcer,
while W07 permits scoped Proxmox resources in a shared root. Those are different
contracts. A shared management endpoint/principal can address multiple explicit
targets; distinct directories do not prove independent resources or failure modes.
If 'state' means observed per-enforcer state, say so. If it means Terraform state,
the shared-root alternative requires an explicit ownership/transaction model.

Required correction: distinguish enforcer_ref, scope/context, connection binding
(endpoint + target selector + credential reference), resource identity, writer,
state namespace and apply/transaction unit. Require unambiguous target selection
and unique resource ownership, not globally unique endpoint/credential strings.
Allow sharing only with declared coupling and validated reconciliation/recovery.
Independent scope attribution must not be presented as independent failure domains.

## R3 — P2: capability -> type -> renderer is underspecified

Location: ADR0119 D1.1 lines 82-97; D2 lines 128-131.

The text does not define which declarations count as a type, how generic and
specific capabilities relate, how multiple enforcement mechanisms on one device
are resolved, or who rejects duplicate renderer registrations. 'One type, one
renderer' also does not distinguish a semantic renderer family from one selected
versioned adapter. Existing offers already bind adapter/provider versions and
jointly compatible strategies; dispatch must preserve those identities.

Required correction: register a closed type-resolution contract with provenance,
explicit 0/1/many outcomes and no priority/first-match fallback. Distinguish OS
classification from enforcement mechanism selection. Resolve exactly one compatible
renderer/adapter contract for each target artifact context, pin its identity/version
before generate, bind it into verification/digests, and fail on unresolved ambiguity.
Several implementations may exist; only one may own a selected target resource set.
Do not create a parallel authored capability registry to solve this.

## R4 — P2: root-per-instance is a choice, not a Terraform limitation

Location: W07 lines 108-126.

'A Terraform root holds one unaliased provider configuration' describes the current
implementation, not a limitation requiring one root per enforcer. Terraform allows
multiple configurations of the same provider through aliases:
[HashiCorp provider configuration](https://developer.hashicorp.com/terraform/language/block/provider#alias).
Root-per-instance is a reasonable isolation choice but must be justified by writer,
state and transaction boundaries. W07 first gives both RouterOS and Proxmox a
complete per-instance root and then makes Proxmox a shared-root exception; specify
which layout is actually selected for each adapter, without turning it into ontology.

Before moving paths, require an old->new resource/state/provider/consumer inventory,
no duplicate ownership, a reviewed state migration and a no-unintended-recreation
plan against the existing state. File rename parity alone cannot prove safe state
migration. This is design preparation, not authorization to migrate state now.

## R5 — P2: erratum must not reverse ADR authority

Location: ADR0110 erratum, paragraph beginning 'The block above is a transcription'.

The phrase 'the file is the authority' is too broad: implemented schema is evidence
of current behavior, not automatically the authority over accepted architecture.
Correct the stale excerpt to the agreed contract or explicitly state the normative
amendment and its reason. Generalizing managed_by_ref beyond routers is sensible,
but the replacement must validate an actual enforcement-capable target, not merely
accept any instance_ref. Capability presence still does not prove qualification.

## R6 — P2: harmonization and evidence are incomplete

AD-01 and AD-08 still need cardinality/ownership terminology synchronized with the
amendment; capability/rule packs and acceptance cases need the same distinctions.
Higher ADR precedence resolves a conflict but does not make contradictory guidance
safe to leave indefinitely. This is part of completing the amendment, not optional
future housekeeping or evidence that implementation is already compliant.

The reported V-04..V-15 matrix is not present in tracked `adr/` or `docs/` at this
revision (`git grep -n -E 'V-04|V-15' -- adr docs` returned no matches). The commit
message summarizes findings, but does not substitute for a referenced matrix.
Publish the exact artifact and links; do not describe an uncommitted session record
as an auditable section of the committed corpus.

## Minimum amendment model (recommendation, not newly accepted schema)

- Device/runtime: placement and management target, not a renderer selector by name.
- Enforcer binding: stable identity, device/target reference, resolved mechanism type.
- Scope: stable intent identity, one enforcer, policy plane and bounded contexts.
- Execution context: scope/enforcer/type, domain/family/hook/chain and applicable modes.
- Selected adapter: versioned rendering/realization contract bound before validation.
- Apply unit: explicit owned resource set, state binding and transaction/recovery boundary.

These are distinctions in existing C->O->I/derived contracts, not a requirement
for six new independently authored entity kinds or plugins.

## Recommended next sequence

1. Resolve R1-R3 cardinality, identity and dispatch; harmonize AD-01/AD-08 and packs.
2. Add tests: two devices of one type; two planes/scopes on one device; multiple
   candidate types; duplicate/missing adapter; shared management endpoint; permutations.
3. Add declared capabilities and derived type, initially without changing legacy
   output. Change matrix index contract and test completeness before any new consumer.
4. Implement per-enforcer projections and prove no cross-instance/plane leakage.
   Single-device parity is necessary but cannot establish multi-device correctness.
5. Separately review artifact-root/state/consumer migration; then qualification gates.

Acceptance of the useful axes does not close W07, G3/G4, backend qualification or
production activation. No runtime test-count claims from the implementation report
were independently repeated as part of this architecture review.
