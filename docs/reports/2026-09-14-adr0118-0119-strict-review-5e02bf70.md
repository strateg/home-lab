## S1 — P1: approved intent не связан с проверенными входами

[topology-tools/plugins/validators/strict_admission.py:129](//wsl.localhost/NixOS/home/nixos/workspaces/home-lab/build/review/5e02bf70/topology-tools/plugins/validators/strict_admission.py#L129); [topology-tools/plugins/validators/security_plan_validator.py:143](//wsl.localhost/NixOS/home/nixos/workspaces/home-lab/build/review/5e02bf70/topology-tools/plugins/validators/security_plan_validator.py#L143).

`evaluate` проверяет только truthiness `approved_intent.approved`; его hash записывается в результат, но ни с чем не сравнивается. Verification record содержит plan digest, но не digest нормализованного intent, с которым validator его сравнивал.

Probe с настоящим результатом registry validator: план scope.a/web допускается с approval для другого scope/binding. Результат `admitted=True`. Можно заменить approved intent после проверки, не меняя ни plan, ни verification.

Исправление: связать approval, проверенный normalized intent и plan точными digest/ссылками и scope/epoch; решение полномочного approver получать по объявленному контракту. Просто добавить поле approver или ещё один непроверяемый digest недостаточно. Доверенный in-process producer и manifest-контракт допустимы; новый криптографический механизм сам по себе не требуется.

## S2 — P1: incomplete/unverified и несовместимые scopes проходят допуск

[topology-tools/plugins/validators/strict_admission.py:116](//wsl.localhost/NixOS/home/nixos/workspaces/home-lab/build/review/5e02bf70/topology-tools/plugins/validators/strict_admission.py#L116); [topology-tools/plugins/validators/strict_admission.py:125](//wsl.localhost/NixOS/home/nixos/workspaces/home-lab/build/review/5e02bf70/topology-tools/plugins/validators/strict_admission.py#L125); [topology-tools/plugins/validators/security_plan_validator.py:147](//wsl.localhost/NixOS/home/nixos/workspaces/home-lab/build/review/5e02bf70/topology-tools/plugins/validators/security_plan_validator.py#L147).

`complete = source['available']` означает только наличие входа. Настоящий validator record с W7002, errors=0, complete=True допускается, хотя SEC-AVAIL не проверен.

Другой probe: `strict_eligible=['other']`, `lowering_complete=[]`, непустой `unlowerable` и пустой `blocked_scopes`. После реальной валидации получен допуск. Проверяется только непустота eligibility, не соответствие scopes плана и checked_scopes. Verification без `errors` и `checked_scopes` тоже принимается: отсутствующее errors трактуется как ноль.

Исправление: типизированный record с обязательными полями и per-obligation/per-scope статусами. Проверять покрытие именно запрашиваемого scope, unlowerable и lowering completeness. Required unverified obligation блокирует соответствующий допуск; не нужно превращать абсолютно все warnings в errors. Явно согласованное пустое Q отличается от отсутствующего Q. Если разрешён scoped admission, renderer должен получать только допущенную проекцию.

## S3 — P1: pipeline tests не доказывают запрет записи и происхождение positive record

[tests/plugin_integration/test_strict_admission_pipeline.py:90](//wsl.localhost/NixOS/home/nixos/workspaces/home-lab/build/review/5e02bf70/tests/plugin_integration/test_strict_admission_pipeline.py#L90); [tests/plugin_integration/test_strict_admission_pipeline.py:117](//wsl.localhost/NixOS/home/nixos/workspaces/home-lab/build/review/5e02bf70/tests/plugin_integration/test_strict_admission_pipeline.py#L117); [tests/plugin_integration/test_strict_admission_pipeline.py:220](//wsl.localhost/NixOS/home/nixos/workspaces/home-lab/build/review/5e02bf70/tests/plugin_integration/test_strict_admission_pipeline.py#L220).

`_run_pipeline` вызывает только compiler и validator. Никакой генератор/writer не исполняется. Затем тест проверяет отсутствие двух заранее указанных каталогов. Поэтому он проходит и без работающего контроля записи. Проверка `legacy_fallback_permitted=False` подтверждает поле результата, не поведение pipeline.

В positive control план меняется, а verification вручную переписывается с новым plan_digest, errors=0, complete=True. Настоящий validator не проверяет именно этот prepared plan в этом тесте; это unit-level fixture записи, не положительный pipeline-контроль.

Исправление без расширения backend scope: тестовый generate-plugin, пишущий marker в tmp_path, с тем же consumer-контрактом допуска, который будет обязателен для renderer. Positive case действительно пишет marker после настоящей проверки точного strict fixture. Negative cases не пишут; mutant обхода допуска должен проваливать тест. Проверять pipeline stage execution, не только два execute_plugin вызова. Не подменять record после проверки.

## S4 — P1: область только с Q всё ещё пропускается

[topology-tools/plugins/validators/security_plan_validator.py:633](//wsl.localhost/NixOS/home/nixos/workspaces/home-lab/build/review/5e02bf70/topology-tools/plugins/validators/security_plan_validator.py#L633).

Сохранился ранний return, если во всём source нет permits и guards. Scope с `policy_overrides: []`, требованием TCP:53 и планом только из terminal получает errors=0, warnings=0, complete=True. При synthetic strict provenance этот результат реально проходит `evaluate`.

Это остаток R1: Q не является подмножеством A, но проверка до него не доходит. При отсутствии списка policy_overrides более ранний continue также пропускает чтение availability.

Исправление: проверять Q и полноту каждой объявленной области независимо от наличия policy overrides. Добавить Q-only и empty-source/nonempty-plan mutants. Подтверждённые исправления обычного Q+permit не закрывают эти варианты.

## S5 — P2: исключение digest слишком широкое

[topology-tools/plugins/validators/strict_admission.py:69](//wsl.localhost/NixOS/home/nixos/workspaces/home-lab/build/review/5e02bf70/topology-tools/plugins/validators/strict_admission.py#L69).

`content_digest` рекурсивно удаляет все поля с именем digest. Probe: изменение `evidence_ref.digest` при неизменной verification не меняет identity и сохраняет допуск. Текущий Mapping API не отвергает такое дополнительное поле.

Исправление: задать schema-defined canonical projection; исключать собственный top-level identity field, а не произвольные вложенные hashes. Если вложенная reference пока не поддерживается, schema должна её отвергать, а не принимать с неучитываемым содержимым.

## S6 — P2: полный конечный диапазон портов роняет построение проб

[topology-tools/plugins/validators/security_plan_validator.py:50](//wsl.localhost/NixOS/home/nixos/workspaces/home-lab/build/review/5e02bf70/topology-tools/plugins/validators/security_plan_validator.py#L50).

`_port_outside(set(range(1, 65536)))` бросает AssertionError. Эти значения разрешены текущим finite-port контрактом. У пустого дополнения не существует представителя, и это нормальный случай, а не нарушение модели.

Исправление: возвращать отсутствие дополнительного класса/представителя, когда весь домен уже перечислен. Для практической масштабируемости перейти от декартова перебора всех значений к проверяемому разбиению на классы эквивалентности или ограничивать ресурсы структурированной диагностикой, не аварией.

## S7 — P1 для воспроизводимости: framework hash включает локальный egg-info

[topology/framework.yaml:26](//wsl.localhost/NixOS/home/nixos/workspaces/home-lab/build/review/5e02bf70/topology/framework.yaml#L26); [tests/test_framework_lock_matches_content.py:26](//wsl.localhost/NixOS/home/nixos/workspaces/home-lab/build/review/5e02bf70/tests/test_framework_lock_matches_content.py#L26).

Чистый git archive 5e02bf70 не проходит snapshot: E7824. Сравнение distribution file rows выявило ровно пять файлов, имеющихся только в локальном дереве:

- topology-tools/home_lab_topology_tools.egg-info/PKG-INFO
- topology-tools/home_lab_topology_tools.egg-info/SOURCES.txt
- topology-tools/home_lab_topology_tools.egg-info/dependency_links.txt
- topology-tools/home_lab_topology_tools.egg-info/requires.txt
- topology-tools/home_lab_topology_tools.egg-info/top_level.txt

Это gitignored installation metadata; distribution включает topology-tools рекурсивно и не исключает egg-info. Поэтому чистый checkout и установленное окружение имеют разный framework hash.

**Уточнение предыдущего review:** объяснение расхождения как lock, обновлённого до последней правки, не было установлено. Теперь проверено: добавление только этих пяти metadata rows к вычислению hashes чистых 12f4e836 и 5d1a0f59 точно восстанавливает hashes их committed locks. Причина — загрязнённый installation metadata состав distribution, а не доказанный неправильный порядок последних правок.

Исправление: исключить installation/build metadata из framework distribution/integrity, обновить lock, проверять hash до и после установки пакета и на чистом checkout. Текущий guard проверяет состояние локального дерева; он полезен, но не доказывает воспроизводимость между этими окружениями. Одного повторного refresh недостаточно.
