## 1. Резюме

Архитектурная основа хорошая, но реализация пока не обеспечивает все заявленные гарантии безопасности и воспроизводимости.

Главная слабость — расхождение между контрактами, исполняемым кодом и проверками: некоторые проверки проходят, не проверяя существенную часть системы. Обнаружены дефекты исполнения subinterpreter worker, генерации firewall, проверки deploy bundle и CI.

Переписывать проект целиком не нужно. Приоритет — сделать уже заявленные архитектурные гарантии реально проверяемыми.

Приоритеты:
- **P1:** исправить до использования затронутого механизма как гарантии безопасной сборки/deployment.
- **P2:** исправить следующим этапом; влияет на надёжность исполнения и проверок.
- Приоритет не означает подтверждённую эксплуатацию уязвимости или сбой работающей инфраструктуры.

## 2. Детальные замечания

### R01. Subinterpreter worker несовместим с API ядра — P1

**Код:** [parallel_executor.py:108–134](/home/nixos/workspaces/home-lab/topology-tools/kernel/scheduler/parallel_executor.py#L108), [PluginExecutionEnvelope](/home/nixos/workspaces/home-lab/topology-tools/kernel/plugin_base.py#L456).

Worker создаёт PluginExecutionEnvelope с отсутствующими полями plugin_id, proposed_context_updates, proposed_diagnostics. Обработчик ошибки сам падает, передавая неподдерживаемый traceback в PluginDiagnostic.

Воспроизведение с успешно выполняющимся синтетическим плагином:
> TypeError: PluginDiagnostic.__init__() got an unexpected keyword argument 'traceback'

Дополнительно worker вызывает execute() вместо общего execute_phase() и не использует стандартный сбор опубликованных сообщений.

**Влияние:** маршрут subinterpreter исполнения не соответствует envelope/phase-контракту ядра.

**Исправление:** после загрузки плагина использовать единый run_plugin_once(), а не отдельную реализацию исполнения и упаковки результата.

**Проверка исправления:** интеграционный тест через настоящий InterpreterPoolExecutor; правильная phase; публикация и потребление данных; обработка исключения без вторичного падения.

**Ограничение доказательства:** воспроизведён непосредственно worker с подменённым loader. Полный end-to-end запуск через interpreter pool в ходе ревью не выполнен.

### R02. Firewall теряет ограничение доступа конкретным VLAN — P1

**Код:** [zone_firewall.tf.j2:114–121](/home/nixos/workspaces/home-lab/topology/object-modules/mikrotik/templates/terraform/zone_firewall.tf.j2#L114).

**Конфигурация:** [inst.security_matrix.mikrotik.yaml:75–81](/home/nixos/workspaces/home-lab/projects/home-lab/topology/instances/network/inst.security_matrix.mikrotik.yaml#L75).

Правило lan-to-management-admin содержит src_vlan_ref: inst.vlan.lan. Шаблон игнорирует это поле и генерирует разрешение из всей zone-user в zone-management.

Рендеринг действующего override подтвердил: в результате присутствуют src_address_list = "zone-user" и dst_address_list = "zone-management", без VLAN-ограничения.

**Влияние:** разрешение шире намерения, записанного в topology.

**Исправление:** разрешать VLAN-reference в конкретное условие фильтрации. Неподдерживаемое ограничение должно вызывать ошибку генерации, а не исчезать.

**Проверка исправления:** тест, различающий доступ из разрешённого VLAN и другого VLAN той же trust zone. Наличие src_vlan_ref должно менять исполняемое правило.

### R03. Proxmox security matrix существует, но enforcement не реализован — P1

**Код:** [firewall_proxmox_generator.py:98–120](/home/nixos/workspaces/home-lab/topology/object-modules/proxmox/plugins/generators/firewall_proxmox_generator.py#L98).

**Конфигурация:** [inst.security_matrix.proxmox.yaml](/home/nixos/workspaces/home-lab/projects/home-lab/topology/instances/network/inst.security_matrix.proxmox.yaml).

В проекте определена матрица изоляции контейнеров. Генератор остаётся STUB: публикует пустые списки артефактов и возвращает успешный результат с информационной диагностикой.

**Влияние:** успешная генерация не подтверждает применение заявленной изоляции. Это не доказательство отсутствия firewall на работающем сервере: состояние устройств не проверялось.

**Исправление:** при активной матрице отсутствие реализации должно блокировать release/deploy. Затем реализовать генерацию и deployment firewall.

**Проверка исправления:** активная матрица плюс STUB завершаются ошибкой; реализованный генератор выпускает ожидаемые артефакты; acceptance-тест проверяет разрешённые и запрещённые соединения.

### R04. Проверка bundle принимает непроверенные артефакты — P1

**Код:** [bundle.py:253–275](/home/nixos/workspaces/home-lab/scripts/orchestration/deploy/bundle.py#L253).

Проверяются только строки из checksums.sha256, без сравнения с фактическим набором файлов.

Воспроизведены оба случая:
- bundle_extra_file_accepted = True: добавленный .tf-файл не обнаруживается.
- bundle_empty_checksum_accepted = True: пустой checksums.sha256 даёт checksums_ok=True.

**Влияние:** нарушается гарантия неизменяемого проверенного входа deployment.

**Исправление:** проверять полное совпадение наборов файлов, обязательные записи, формат хешей, дубликаты и выход путей за границы bundle. Проверку происхождения bundle отделить от проверки контрольных сумм.

**Проверка исправления:** добавление, удаление и изменение файла; пустой или усечённый checksum-файл; дубликаты; некорректные и выходящие за корень пути.

### R05. Расшифрованные секреты получают слишком широкие права — P1

**Код:** [bundle.py:91–104](/home/nixos/workspaces/home-lab/scripts/orchestration/deploy/bundle.py#L91).

Секреты записываются через обычный write_text(), без явного ограничения доступа.

На синтетических данных в текущем WSL:
- каталог bundle: 0755;
- файл секрета: 0644.

**Влияние:** при доступных родительских каталогах секреты могут читать другие локальные пользователи. Защита зависит от внешнего umask.

Реальные секреты для проверки не расшифровывались: использовалась подмена результата decrypt.

**Исправление:** каталоги с секретами 0700, файлы 0600; минимально необходимый набор секретов; явная политика хранения и удаления.

**Проверка исправления:** создание bundle при разных umask и проверка прав после перемещения временного bundle в итоговое расположение.

### R06. Manifest/cycle gates пропускают framework shards — P1

**Код:** [check_plugin_cycles.py:29–65](/home/nixos/workspaces/home-lab/scripts/validation/check_plugin_cycles.py#L29), [validate_plugin_manifests.py](/home/nixos/workspaces/home-lab/scripts/validation/validate_plugin_manifests.py).

**Manifest:** [plugins.yaml](/home/nixos/workspaces/home-lab/topology-tools/plugins/plugins.yaml).

Корневой manifest содержит plugins: [] и includes, но рассматриваемые проверки не обходят включения.

Фактический результат:
- cycle gate сообщил проверку **8 плагинов**;
- во framework shards найдены ещё **97 записей плагинов**.

**Влияние:** отдельные gates не подтверждают валидность всего набора framework-плагинов. Runtime может выполнять дополнительные проверки; вывод не означает отсутствие любой защиты.

**Исправление:** общий resolver manifest/includes для runtime и validation с одинаковым порядком discovery.

**Проверка исправления:** сравнение наборов проверенных и обнаруженных runtime plugin IDs; некорректный entry и цикл внутри shard должны давать ненулевой exit code.

### R07. Secret scan может завершиться успешно при ошибке Git — P1

**Код:** [python-checks.yml:145–167](/home/nixos/workspaces/home-lab/.github/workflows/python-checks.yml#L145).

git fetch и git diff запускаются с check=False. Код возврата diff игнорируется. Пустой stdout трактуется как отсутствие изменённых файлов и приводит к exit 0.

**Влияние:** при недоступной базе сравнения, например в shallow checkout, ошибка определения файлов может превратиться в успешную проверку без сканирования.

Дополнительно исключён целиком каталог projects/*/secrets/: случайный plaintext-файл в нём этот scanner не проверит.

**Исправление:** ошибка определения diff должна останавливать gate; необходимые Git refs должны быть доступны; для секретных каталогов нужна проверка encrypted-формата вместо полного исключения.

**Проверка исправления:** отсутствующая base revision, ошибка fetch, shallow history, пустой корректный diff, синтетический plaintext-файл в secrets-каталоге.

**Ограничение:** статический анализ workflow; GitHub Actions в ходе ревью не запускался.

### R08. Plugin CI не устанавливает зависимость своих команд — P2

**Код:** [plugin-validation.yml:58–69](/home/nixos/workspaces/home-lab/.github/workflows/plugin-validation.yml#L58), [test.yml:19](/home/nixos/workspaces/home-lab/taskfiles/test.yml#L19).

Workflow устанавливает pytest, но не pytest-xdist; вызываемые tasks используют -n auto.

**Влияние:** в чистом окружении без xdist pytest не принимает эти аргументы.

**Исправление:** единый способ установки dev-зависимостей локально и во всех CI jobs, желательно из lock-файла.

**Проверка исправления:** запуск соответствующих tasks в чистом окружении, подготовленном строго шагами workflow.

**Ограничение:** чистое CI-окружение не создавалось; подтверждено расхождение конфигураций установки и запуска.

### R09. Timeout не ограничивает ожидание parallel worker — P2

**Код:** [phase_executor.py:372–378](/home/nixos/workspaces/home-lab/topology-tools/kernel/scheduler/phase_executor.py#L372).

Сначала as_completed(futures) без timeout ждёт завершения задачи. Только после этого вызывается future.result(timeout=...), когда ограничивать ожидание уже поздно.

**Влияние:** зависший worker может блокировать фазу независимо от manifest timeout.

**Исправление:** deadlines от момента отправки задачи и отдельная стратегия остановки зависшего исполнения. Отмена future сама по себе не останавливает уже работающий код.

**Проверка исправления:** bounded-тест с медленным worker завершается в заданном бюджете и выдаёт timeout-диагностику; shutdown executor также не должен зависать.

**Ограничение:** статический анализ кода; бесконечно работающий worker не запускался.

## 3. Архитектурная оценка

### Сильные стороны

- Чётко определена модель Class → Object → Instance.
- Разделены lifecycle-стадии, manifest-контракты и deployment bundles.
- Есть ADR, lock-проверки и значительный тестовый набор.
- Проверка framework integrity действительно блокирует несовпадение.

### 3.1. Дублирование бизнес-логики безопасности

Матрица вычисляется в [security_matrix_compiler.py](/home/nixos/workspaces/home-lab/topology-tools/plugins/compilers/security_matrix_compiler.py), затем повторно в [MikroTik projections](/home/nixos/workspaces/home-lab/topology/object-modules/mikrotik/plugins/projections.py#L575).

Projection дополнительно читает object properties с диска. Это два места принятия одного решения, способные расходиться, и зависимость генерации от источников вне уже подготовленной политики.

**Целевое направление:** compiler выпускает единую нормализованную политику; генераторы только переводят её в платформенные правила. Поддержку policy-ограничений нужно явно валидировать для выбранного enforcer.

### 3.2. Успешность этапа не равна выполнению контракта

Примеры: Proxmox STUB, неполная проверка manifests, неполная проверка bundle.

**Целевое направление:** проверять ожидаемые результаты и полноту входов/артефактов, а не только отсутствие исключений или наличие отдельных файлов.

### 3.3. Недостаточная проверка реальных границ системы

Проходящие целевые тесты не обнаружили воспроизведённые дефекты worker и bundle.

**Целевое направление:** негативные тесты, настоящий executor, чистое CI-окружение, тесты семантики firewall и проверки равенства наборов артефактов/плагинов.

## 5. Рекомендуемый порядок работ

1. **Безопасность policy enforcement:** исправить потерю VLAN-ограничения и успешный Proxmox STUB.
2. **Безопасность bundle:** полная проверка состава и контрольных сумм, права на секреты.
3. **Надёжность runtime:** единый worker/execution contract и корректные deadlines.
4. **Достоверность CI:** единое discovery, ошибки scan как ошибки gate, согласованные зависимости.
5. **Архитектурное упрощение:** устранить повторное вычисление security matrix.
6. После проверки доверенных изменений актуализировать framework lock и выполнить полную компиляцию, targeted regression-тесты и интеграционные gates.

Для каждого исправления сначала следует добавить тест, воспроизводящий дефект. Изменения архитектурных контрактов необходимо оформить через ADR и adr/REGISTER.md.

## 6. Заключение

Основной риск проекта — не отсутствие архитектуры, а неполная реализация её гарантий. Topology-first, изоляция исполнения, immutable bundles и fail-safe validation должны подтверждаться одинаково строгими runtime- и CI-проверками.

Приоритет следующей итерации — закрыть перечисленные разрывы и добавить тесты на реальных границах системы, а не расширять количество архитектурных механизмов.
