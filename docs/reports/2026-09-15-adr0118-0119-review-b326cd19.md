# ADR0118/0119: повторное ревью strict admission на b326cd19

Дата: 2026-09-15. Исходный запрос: проверить `8dada8ef`, `6513a27d`. За время паузы HEAD продвинулся до `b326cd19`; исправление `31ebefb9` также включено в ревью. Остальные новые изменения F3–F5 и W05 не получили здесь полного ревью.

## Решение

**Changes requested: один подтверждённый P1 — неполное покрытие terminal default deny.** Прежние конкретные контрпримеры R1–R5 и три замечания из промежуточного сообщения исправлены. Это не закрывает PR2 / strict admission / G3: остаётся воспроизводимый допуск плана с незавершённым исполнением внутри уже поддерживаемой области.

Production-код не менялся. ADR: not required — это отчёт о соответствии существующему контракту, а не новое архитектурное решение.

## F1 — P1: неполный terminal default deny проходит validator, admission и writer

### Места в коде

- `topology-tools/plugins/validators/security_plan_validator.py:319–357`: проверяются наличие terminal и его effect, но не полнота его предиката.
- Тот же файл, `:882–906`: `unsupported` не является ошибкой, если поток не входит в Q; проверяются лишние accept и потерянные обязательные потоки.
- Тот же файл, `:1184–1189`: terminal фильтрует endpoints, но возвращает deny без проверки transport.
- `topology-tools/plugins/validators/strict_admission.py:303–364`: проверка формы допускает конечный transport и ограниченные endpoints у terminal; межполевое ограничение роли отсутствует.

Нормативная основа: `adr/0119-analysis/FORMAL-CONTRACT.md:72–75`: каждое достижимое исполнение должно завершаться допустимым исходом либо проваливать валидацию; reachable default deny покрывает остаточные потоки. Это отдельное обязательство, не производное от наличия Q.

### Воспроизведение

Использован положительный pipeline fixture: разрешён TCP/53 из z.a в z.b, этот же поток явно требуется Q. Strict provenance подготовлен тестом; record каждый раз публикует настоящий валидатор после проверки изменённого плана. Approval соответствует фактическим intent/evidence digest, ожидаемая epoch передана. Record вручную не исправляется.

**Вариант A — область terminal сужена:**

```yaml
terminal: true
effect: deny
sources: [z.a]
destinations: []
transport: {kind: any}
```

Поток `z.b -> z.a UDP/9999` принадлежит замкнутому endpoint-множеству источника. `_interpret` возвращает `unsupported`, но валидатор публикует `errors=0` и четыре `pass`. Admission принимает план. Настоящий test-only generator на стадии generate записывает marker с этим terminal.

Этот контрпример не зависит от будущей трактовки transport рендерером: сам действующий интерпретатор показывает отсутствие конечного решения, а проверка это пропускает. На backend с default allow незакрытый остаток особенно опасен; проверок на реальном устройстве здесь не было.

**Вариант B — transport terminal сужен:**

```yaml
terminal: true
effect: deny
sources: []
destinations: []
transport: {kind: ports, protocol: tcp, ports: [53]}
```

Для того же UDP-потока интерпретатор возвращает deny, потому что не читает transport terminal. При этом projection и записанный marker сохраняют конечный TCP/53-предикат. Получается противоречивый контракт: verifier доказывает безусловный deny, а потребителю отдаётся ограниченный предикат. Validator снова даёт `errors=0`, admission проходит, marker записывается.

Сужение `destinations` до `[z.b]` также проходит независимую верификацию и admission; запись marker отдельно проверена для вариантов A и B.

### Исправление и критерий закрытия

1. Зафиксировать проверяемый инвариант terminal в рамках текущей грамматики: `deny`, последняя позиция, transport `any`, покрытие всей заявленной области endpoints. Для текущей канонической формы с пустыми списками endpoints можно требовать именно эту форму; если допускается явное перечисление, доказать полноту относительно независимого scope inventory.
2. Не игнорировать `unsupported` ни для одного in-scope представителя, независимо от Q. Недоказанное завершение — отказ или unverified с блокировкой admission, а не отсутствие ошибки.
3. Не исправлять это превращением всякого `unsupported` в deny: такой fallback приписал бы плану правило, которого он не несёт.
4. Сохранить единый смысл terminal между verifier и projection. Если поле transport фиксировано ролью, запретить противоречивое значение на входе, а не молча игнорировать его.
5. Добавить негативные pipeline-тесты на ограниченные source, destination и transport terminal; утверждать отсутствие marker. Положительный контроль с полнообластным terminal должен по-прежнему записываться. Поток контрпримера обязан находиться вне Q — иначе тест проверит только доступность и снова не защитит termination.

Не требуется реализовывать новый backend, approval producer или расширять F3–F5. Дефект находится в уже реализованном ограниченном интерпретаторе и его admission-контракте.
