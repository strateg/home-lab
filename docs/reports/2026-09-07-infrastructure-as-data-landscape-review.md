## 1. Главный вывод

**Подход современный и обоснованный. Реализация пока не доказывает зрелость, соответствующую широте заявленного framework.**

home-lab — не просто коллекция Terraform/Ansible и не попытка заменить Terraform. Это **предметный компилятор инфраструктуры**: модель устройств, сетей, размещения и сервисов преобразуется в несколько согласованных наборов артефактов; Terraform и Ansible остаются исполнительными инструментами.

Главное достоинство — возможность выразить инфраструктурное намерение один раз и проверить связи между несколькими технологическими доменами. Главная слабость — стоимость собственного языка, runtime, discovery, release/deploy-инструментария и системы правил при ещё не закрытых базовых границах корректности.

**Оценка назначения:**
- Для собственного разнородного стенда и исследовательской платформы — полезный, содержательный проект.
- Для переноса на другие реальные стенды — перспективный кандидат, но переносимость пока доказана ограниченно.
- Для универсальной production-ready платформы — доказательств недостаточно; текущие блокирующие замечания этому противоречат.
- Для дальнейшего развития — сохранить предметную модель, уменьшать дублирование и доказывать эксплуатационные свойства, а не наращивать количество расширений.

Это инженерная оценка, не сертификация. Единой универсальной шкалы зрелости Infrastructure-as-Data здесь не применяется.

## 3. Оценка по актуальным инженерным ориентирам

### 3.1. Сводная матрица

| Область | Сильная сторона | Ограничение / оценка |

| Декларативный источник истины | Class → Object → Instance; проектные данные отделены от общих модулей | Сильная основа; поздние чтения исходных YAML генераторами ослабляют однозначность модели |
| Предметная семантика | Сети, VLAN, trust zones, capabilities, размещение и сервисы связаны общей моделью | Это основная ценность; корректность междоменных связей важнее количества генераторов |

### 3.2. GitOps: правильная база, но не подтверждён полный цикл

OpenGitOps выделяет декларативное состояние, неизменяемую версионированную историю, автоматическое получение желаемого состояния агентами и непрерывное согласование фактического состояния с желаемым. [OpenGitOps Principles](https://opengitops.dev/).

У home-lab хорошо выражены декларативная модель и компиляция из версионируемых данных. Есть drift-related проверки и rehearsal-механизмы. Однако в исследованных материалах не подтверждён полный непрерывный контроллер observed → desired → remediation для всей инфраструктуры.

Это **не делает IaD-подход неправильным**. Для домашнего маршрутизатора бесконтрольное автоматическое исправление может быть хуже режима «выявить drift → показать план → получить разрешение → применить». Корректнее позиционировать систему как compiler-first, GitOps-compatible automation, не подменяя этим доказательство всех четырёх принципов.

Рекомендация: сначала обеспечить read-only сбор наблюдаемого состояния, semantic diff и историю расхождений; автоматический apply вводить только для явно безопасных классов изменений.

### 3.3. Supply chain: механизмы есть, совместимость и гарантии требуют доводки

Нельзя говорить, что в проекте отсутствуют подписи и provenance: соответствующие задачи действительно есть в [framework.yml](/home/nixos/workspaces/home-lab/taskfiles/framework.yml).

Но [generate-framework-provenance.py:57–78](/home/nixos/workspaces/home-lab/topology-tools/utils/generate-framework-provenance.py#L57) формирует custom JSON с predicate_type, builder и source на верхнем уровне. Это не стандартный in-toto Statement с predicateType и вложенным predicate.buildDefinition/runDetails, описанный форматом SLSA Build Provenance. [SLSA Build Provenance](https://slsa.dev/spec/v1.2/build-provenance).

**Вывод:** metadata полезны для собственного verifier, но ссылка на SLSA URI не обеспечивает совместимость с внешними инструментами. Предлагается стандартный attestation и отдельный тест его проверки независимым потребителем. Подпись должна связывать проверенный артефакт, источник, workflow/builder и политику доверия.

Оговорка: SLSA v1.2 рекомендует конкретные форматы attestations, но не делает их единственно обязательными. Поэтому замечание — об интероперабельности и недоказанных гарантиях, а не автоматический вердикт «нарушен любой уровень SLSA». Уровень SLSA в этом ревью не присваивается. [SLSA v1.2](https://slsa.dev/spec/v1.2/).

### 3.4. Сетевая безопасность: zone-based policy не равна Zero Trust

[security_matrix_compiler.py:413–420](/home/nixos/workspaces/home-lab/topology-tools/plugins/compilers/security_matrix_compiler.py#L413) автоматически разрешает переход из зоны с большим security_level в меньшую, если раньше не сработало другое правило. Это понятный SOHO-профиль, но не универсальное применение least privilege.

Уже есть полезное различение enforcement planes: same-zone на internal plane по умолчанию запрещается. Поэтому было бы неверно утверждать, что абсолютно весь внутренний трафик разрешён.

Для критичных сервисов стоит предложить отдельный строгий профиль: default-deny, явно заданные сервисные потоки, порты, enforcer и объяснение причины разрешения. При этом сетевые ACL не заменяют идентичность, аутентификацию и авторизацию сервисов. NIST Zero Trust не допускает доверие только из-за сетевого расположения. [NIST SP 800-207](https://csrc.nist.gov/pubs/sp/800/207/final).

Изменение текущей R1–R6 политики — отдельное архитектурное решение с ADR и миграционным планом, а не тихая правка defaults по итогам ревью.

## 4. Самые важные слабые места

### A. P1 — Разрыв между декларацией защиты и реальным enforcement

Повторное ревью показало, что Proxmox guard читает неканоническую форму compiled model и возвращает SUCCESS/STUB при каноническом входе с активной security matrix.

Код: [firewall_proxmox_generator.py:103–111](/home/nixos/workspaces/home-lab/topology/object-modules/proxmox/plugins/generators/firewall_proxmox_generator.py#L103).

Архитектурно это опаснее ошибки форматирования: система может принять декларацию намерения за обеспеченную защиту. Требуется инвариант: каждый активный security intent либо имеет поддерживаемый и проверенный enforcer, либо блокирует выпуск deployable bundle.

### B. P1 — Bundle не является замкнутой доверенной единицей

Проверка строкового префикса пути вместо принадлежности каталогу допускает внешний symlink на соседний каталог с похожим именем. Это воспроизведено в повторном ревью.

Код: [bundle.py:302–307](/home/nixos/workspaces/home-lab/scripts/orchestration/deploy/bundle.py#L302).

Нужны явная symlink policy, component-aware containment, проверка полного manifest и защита от изменения проверенного содержимого до использования. Контент, который проверен, должен совпадать с контентом, который исполняется. Этот отчёт не устанавливает возможность эксплуатации удалённым атакующим: она зависит от доступа к bundle/workspace.

### C. P2 — Семантика инфраструктуры вычисляется более чем в одном месте

Security matrix обрабатывается компилятором и MikroTik projection; projection также читает object YAML с диска. См. [security_matrix_compiler.py](/home/nixos/workspaces/home-lab/topology-tools/plugins/compilers/security_matrix_compiler.py), [projections.py:104](/home/nixos/workspaces/home-lab/topology/object-modules/mikrotik/plugins/projections.py#L104), [projections.py:575](/home/nixos/workspaces/home-lab/topology/object-modules/mikrotik/plugins/projections.py#L575).

**Риск:** один и тот же intent может получить разные defaults, reference resolution или interpretation на разных backend.

Предлагаемая граница:
1. Front-end читает и нормализует источники.
2. Semantic compilation единожды разрешает ссылки, capabilities, inheritance и политики.
3. Валидируется версионированная effective model / IR.
4. Generators только переводят проверенную семантику в backend-specific формат.

Это не предложение сломать установленный six-stage lifecycle: речь о контракте данных внутри существующих стадий.

### D. P2 — Runtime обещает больше, чем обеспечивает deadline

При timeout=1 s настоящий subinterpreter worker с задержкой 1,4 s дал SUCCESS. Worker с задержкой 7 s дал FAILED, но стадия вернулась только после его завершения. См. [phase_executor.py](/home/nixos/workspaces/home-lab/topology-tools/kernel/scheduler/phase_executor.py) и воспроизведения в повторном отчёте.

Нужны отдельные гарантии:
- поздний результат не публикуется;
- ожидание стадии ограничено;
- зависшее выполнение можно остановить либо безопасно изолировать;
- отказ одного плагина не оставляет частично принятые публикации.

Не следует считать subinterpreter сам по себе границей безопасности для произвольного недоверенного plugin-кода. Если нужны сторонние недоверенные плагины, модель угроз и изоляция должны проектироваться отдельно.

### E. P2 — Число тестов маскирует разрыв с release readiness

В сегодняшнем повторном ревью: **165 passed, 1 skipped** для выбранного набора. Одновременно:
- framework lock verification — FAIL, E7824;
- strict manifests — FAIL из-за двух warnings;
- quality-fast — FAIL, Black требует форматирования 14 файлов;
- в plugin-validation workflow остаётся отсутствие pytest-xdist для вызовов с -n auto.

Полный CI и аппаратный E2E не объявляются пройденными. Не все formatting-проблемы обязательно введены последними исправлениями.

В [FRAMEWORK-V5.md](/home/nixos/workspaces/home-lab/docs/framework/FRAMEWORK-V5.md) стоит Production-ready. На проверенной ревизии такое общее заявление не подтверждено. Лучше публиковать матрицу готовности по функциям и backend с датой и ссылкой на evidence, а не единый статус для всей платформы.

### F. P2 — AI-rules снижают объём контекста, но уже расходятся с моделью

[docs/ai/rules/topology-model.md:40–47](/home/nixos/workspaces/home-lab/docs/ai/rules/topology-model.md#L40) описывает L0 как Physical, L1 как Network, L2 как Storage, L7 как Access.

В [topology/layer-contract.yaml](/home/nixos/workspaces/home-lab/topology/layer-contract.yaml) действуют L0=meta, L1=foundation, L2=network, L3=storage, L7=operations. Направление этой модели также отражено в [ADR0062](/home/nixos/workspaces/home-lab/adr/0062-modular-topology-architecture-consolidation.md).

**Последствие:** агент может точно следовать краткой инструкции и всё равно выбрать неверный слой.

Нужна не ещё одна копия правил, а проверка семантического соответствия. Машиночитаемые таблицы желательно выводить из канонического контракта; для текстовых правил — ADR source, область применимости, проверяемый инвариант и тест. Наличие source_adr и успешная проверка ссылок не доказывают совпадение смысла.

### G. P2 — Слишком широкий framework относительно доказанного переиспользования

Есть 105 обнаруженных плагинов; около 134 тыс. физических строк отслеживаемых Python-файлов **включая тесты**, не только production runtime. Это индикатор поверхности сопровождения, не самостоятельное доказательство плохого кода.

[projects/test-lab/project.yaml](/home/nixos/workspaces/home-lab/projects/test-lab/project.yaml) прямо имеет status: validation-fixture. Это полезный тест N>1, но ещё не реальная независимая эксплуатация framework.

Риск — оплачивать сложность платформенного продукта до подтверждения повторного использования. Лучший следующий эксперимент: второй существенно отличный стенд без правок общих модулей под его имена и адреса.

| **Kratix** | Promise связывает API, dependencies, workflows и destinations. [Promises](https://docs.kratix.io/main/reference/promises/intro) | Если развивать продуктовые инфраструктурные услуги и self-service. Это сравнение платформенной оркестрации, не доказательство необходимости заменить batch compiler контроллером |
| **CUE** | Данные, ограничения и валидация в общей модели; генерация конфигурации. [Введение](https://cuelang.org/docs/introduction/) | Строительный блок для schema/constraint layer, а не полный deploy framework. Unification не равна произвольному override/deep-merge; миграция собственного DSL потребует проверки семантики |
| **NetBox** | Network source of truth: IPAM/DCIM, устройства, виртуализация, связи, API и расширения. [Документация](https://netboxlabs.com/docs/netbox/) | Образец инвентарной модели либо upstream inventory. Не делать двунаправленную синхронизацию Git ↔ NetBox без однозначного владельца каждого вида данных |

**Что изучать первым:**
1. Kapitan — сокращение собственного общего compiler/templating plumbing.
2. Infrahub — граф, schema evolution, lineage, review инфраструктурных данных.
3. Commodore — промышленная организация reusable framework/components.
4. Nautobot Design Builder — жизненный цикл design-owned instances.
5. Остальные — по конкретной задаче, не как обязательный целевой стек.

Среди изученных решений не подтверждена готовая drop-in замена всей комбинации home-lab: физическая топология + RouterOS + Proxmox + Linux configuration + общие сетевые/placement-инварианты + offline artifacts. Это не утверждение об уникальности проекта во всём мире.

## 6. Что сохранить, а что перестать разрабатывать самостоятельно

### Сохранить как предметную ценность

- Модель связей между сетями, устройствами, размещением и сервисами.
- Capability-based выбор поддерживаемого поведения.
- Проверки согласованности до Terraform/Ansible apply.
- Генерацию нескольких артефактов из одной проверенной семантики.
- Evidence-based workflow, отделение framework/project и topology-first remediation.

### Консолидировать или переиспользовать

- Один manifest resolver вместо нескольких слегка разных реализаций.
- Один набор semantic transforms вместо повторного вычисления defaults/security в backend.
- Типовые signing/attestation formats вместо собственного несовместимого формата.
- Один воспроизводимый способ установки toolchain для разработчика и CI.
- Общие schema/tooling механизмы, если небольшой прототип докажет реальное сокращение сложности.

**Не рекомендую сейчас:**
- полную перепись на CUE/Nix/Crossplane;
- переход с файлов на graph database без потребности в API/многопользовательском редактировании;
- превращение каждого helper в plugin;
- новый универсальный слой абстракции поверх уже существующих шести стадий;
- использование AI как доверенного генератора применяемой инфраструктуры без deterministic validation.

## 7. Когнитивная нагрузка: краткий SWOT

Этот раздел учитывает цель, сформулированную в ai-rules.txt.

| Сторона | Оценка |
|---|---|
| Strengths | ADR-derived rulebook и scoped packs уменьшают необходимость читать весь репозиторий; canonical topology сокращает повторный ввод данных |
| Weaknesses | Собственный DSL, шесть стадий, множество entrypoints и конфликтующие краткие справочники заставляют человека/AI помнить слишком много исключений |
| Opportunities | Автоматическое извлечение справочных таблиц; semantic consistency tests; команда объяснения effective value; минимальный task-oriented контекст |
| Threats | Краткая, но устаревшая инструкция выглядит авторитетной; тесты наличия ключевых слов могут сохранять неверный смысл; новые агенты размножают локальные обходы |

Практические меры:
1. Загружать сначала compact rulebook, затем только пакеты задачи; не все ADR по умолчанию.
2. Добавить machine-readable rule → invariant → validating test → evidence mapping.
3. Для каждого effective field показывать source file, inheritance chain, override и итоговое значение.
4. Измерять время выполнения типовой задачи и частоту повторных ошибок, а не только число токенов.
5. Превратить выявленное расхождение L0–L7 в regression test правил.
6. Свести основные пользовательские сценарии к небольшому стабильному набору task-команд с одинаковой диагностикой.

Добавление нового rule pack оправдано только если оно убирает необходимость держать исключение в памяти, а не создаёт ещё один источник истины.

## 8. Приоритетный план с критериями приёмки

### Этап 1 — Закрыть доверенные границы и красные gates

- Закрыть Proxmox fail-open, bundle symlink, deadline, missing include/cycle handling и CI dependency.
- Добавить постоянные негативные тесты на воспроизведённые случаи.
- Привести source/lock в согласованное состояние осознанным refresh после проверки изменений.
- Исправить semantic drift AI-rules.
- Получить зелёные relevant tasks, strict framework/manifests и полный CI на чистом checkout.

**Приёмка:** заведомо неподдерживаемая защита блокирует bundle; внешний файл не попадает в исполнение; просроченный worker не публикует SUCCESS; свежая CI-среда собирается без ручных зависимостей.

### Этап 2 — Стабилизировать внутреннюю модель и объяснимость

- Версионировать effective model/IR.
- Убрать позднее переосмысление исходной topology из generators.
- Проверять схемы на границах и полноту producer/consumer contracts.
- Добавить source provenance для итоговых значений и semantic diff.
- Проверять invariants: переименование instance не меняет security; перестановка независимых входов не меняет output; неизвестная обязательная ссылка не расширяет разрешения.

**Приёмка:** одинаковый intent даёт одинаковую политику во всех поддерживаемых backend; каждое критичное правило можно объяснить от source до артефакта.

### Этап 3 — Доказать выпуск и эксплуатацию

- Две сборки в чистых одинаково зафиксированных окружениях; сравнение содержимого с явно исключёнными nondeterministic metadata.
- Стандартная проверяемая attestation и проверка tampered artifact.
- Разделить публикуемые артефакты и приватные runtime materializations с секретами; не менять approved injection path без ADR.
- Drift detection, approved plan/apply, post-deploy assertions.
- Восстановление тестового сервиса вместе с данными; отдельно проверить state и credentials recovery.

**Приёмка:** оператор может развернуть и восстановить поддерживаемый сценарий по runbook, без скрытых знаний автора. IaC rollback сам по себе не считается восстановлением пользовательских данных.

### Этап 4 — Проверить необходимость framework как продукта

- Подключить второй реальный, заметно отличный проект.
- Выполнить clean installation, compile, plan и согласованный E2E.
- Записать необходимые изменения общего framework и затраты оператора.
- Только после этого расширять API поддержки, backends и distribution.

**Приёмка:** framework переиспользуется через данные/контракты, а не условные ветки под второй стенд.

### Небольшой сравнительный эксперимент вместо переписывания

Взять один существующий вертикальный сценарий: host + workload + VLAN + service → Terraform + Ansible. Сравнить текущий путь с прототипом, использующим Kapitan для общей генерации, либо CUE для одного участка ограничений.

Измерять:
- сколько предметного кода осталось неизбежным;
- число преобразований и конфигурационных файлов;
- понятность ошибок;
- сохранность null/false/zero, overrides и reference semantics;
- воспроизводимость output;
- трудоёмкость добавления второго варианта.

Не совмещать несколько новых платформ в одном эксперименте. Миграцию рассматривать только при измеримом выигрыше.

## 9. Итоговая рекомендация

**Сохранять Infrastructure-as-Data, но уменьшать собственную платформенную механику и усиливать доказательства корректности.**

Сейчас проекту нужнее:
- один достоверный semantic model;
- замкнутая цепочка intent → validated model → verified artifact → approved execution;
- измеримая переносимость;
- согласованные, проверяемые правила;
- понятное восстановление после ошибки.

Не количество YAML, ADR, плагинов или зелёных unit-тестов определяет зрелость, а возможность безопасно и объяснимо получить нужную инфраструктуру, обнаружить расхождение и восстановить сервис.

**Краткая формула оценки: сильная предметная архитектура; слишком широкая собственная инфраструктура разработки; недостаточно доказанная эксплуатационная зрелость.**
