--diagnostics по умолчанию выключен. artifact_owner теперь возвращает disabled для effective_json. EffectiveJsonGenerator действительно прекращает работу при таком owner. Но emit_effective_artifact различает только core и «всё остальное»: после generate он требует существования output_json независимо от disabled.

**Независимое воспроизведение:** вызваны реальные artifact_owner, EffectiveJsonGenerator и emit_effective_artifact, со свежим синтетическим compiled_json и временным output, без запуска остальных генераторов.

| Файла нет | E3001: effective JSON artifact was not generated by plugins; файл не создан |
| Есть JSON с содержимым {"stale": true} | I9001 Compile success; старый файл остался без изменений |

Таким образом результат зависит от мусора предыдущего запуска. Это не гипотеза о deployment, а воспроизведённый дефект связки ownership → generator → finalizer. Полный production build в этом ревью не запускался.

**Связанный разрыв orchestration:** [scripts/orchestration/lane.py:100](/home/nixos/workspaces/home-lab/scripts/orchestration/lane.py#L100) запускает compiler без --diagnostics, а следующим шагом [scripts/orchestration/lane.py:117](/home/nixos/workspaces/home-lab/scripts/orchestration/lane.py#L117) передаёт build/diagnostics/report.json governance-validator. На чистом workspace его не будет; при наличии старого отчёта проверяться может прошлый запуск. Deploy command builder также задаёт output/diagnostics paths, но не включает новый флаг: [scripts/orchestration/deploy/workspace.py:124](/home/nixos/workspaces/home-lab/scripts/orchestration/deploy/workspace.py#L124). Эти последствия установлены по коду entrypoints, не через реальный deploy.

**Рекомендация:** разделить canonical effective artifact и необязательную диагностическую выгрузку. Если выключение effective output действительно нужно, явно поддержать disabled во всех consumers/finalizers и обновить lane/deploy entrypoints. ### F02 — P2 / новая регрессия: отсутствующий SOHO profile превращается в невалидный существующий

**Места:** [topology-tools/plugins/compilers/soho_profile_resolver_compiler.py:35](/home/nixos/workspaces/home-lab/topology-tools/plugins/compilers/soho_profile_resolver_compiler.py#L35) и [topology-tools/plugins/validators/soho_product_profile_validator.py:93](/home/nixos/workspaces/home-lab/topology-tools/plugins/validators/soho_product_profile_validator.py#L93).

При отсутствии product_profile compiler публикует:
- soho_profile_resolution.profile_present = false;
- project_product_profile = {}.

Validator проверяет только isinstance(product_profile, dict). Пустой dict проходит эту проверку, поэтому legacy-ветка W7941 становится недоступна для штатного compiler output. Затем JSON Schema отклоняет отсутствие profile_id.

**Воспроизведение:** реальный compiler → общий PluginContext → реальный validator. Только загрузчик project manifest заменён синтетическим {"project": "audit"}; публикации не подделывались. Migration policy отсутствует, то есть legacy sunset не включён.

Результат:
- compile: SUCCESS, profile_present=false;
- validate: FAILED, E7941;
- сообщение: product_profile schema validation failed: 'profile_id' is a required property.

Текущий home-lab с заданным профилем проходит compile/validate. Дефект касается поддерживаемого legacy/missing-profile сценария, а не каждого проекта.

**Рекомендация:** проверять явно profile_present либо согласовать nullable-контракт. Не использовать просто «if not product_profile»: реально заданный пустой профиль и отсутствие профиля должны различаться. Сохранить отдельные sunset-проверки.
