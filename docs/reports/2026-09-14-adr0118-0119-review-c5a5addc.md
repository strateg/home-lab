# ADR0118/0119: external code review of c5a5addc

Date: 2026-09-14. Reviewed changes: `782061e8`, `c5a5addc`; baseline: `5e02bf70`.

## Verdict

**PR2 / strict admission: changes requested. G3 remains open.**

The fixes materially improve the boundary: the validator derives intent identity independently; verification carries per-scope obligation statuses; a real generate-stage fixture writes a marker; its positive control uses the actual validator; nested digest references are refused; finite port membership is partitioned into equivalence classes; a tracked-only source tree now verifies its framework lock without installation metadata.

This review nevertheless reproduces two blocking admission/consumption failures and three narrower contract gaps. These are not evidence of a currently deployed firewall bypass: the production plan remains `legacy_shadow`, there is no production approval producer, and the positive controls prepare strict provenance in a fixture. The findings concern the boundary intended for future strict consumers.

Implementation code was not modified. Counterexamples use the real compiler/validator helpers, not hand-written successful verification records.

## Findings

### R1 — P1: projection can consume another plan under an existing admission

Source: `topology-tools/plugins/validators/strict_admission.py:407–431` (`admitted_projection`).

The function checks `admission.admitted` and filters scope names, but does not recompute the supplied plan's digest against `admission.plan_digest`. It also returns the original mutable rule mappings.

Reproduction:

1. Compile and independently validate the positive fixture; obtain a valid approval and admission.
2. Deep-copy its plan and replace the first rule's finite transport with `{kind: any}`.
3. Pass that changed plan and the old admission to `admitted_projection`.
4. The result contains the changed rule and the **old admitted digest**.
5. Separately, modifying a rule in a returned projection modifies the original plan.

`evaluate` protects mutation before evaluation, but the consumer API reopens the gap after evaluation. The current test writer calls these functions consecutively; this review does not claim an intervening mutation occurs in that writer today.

**Required correction:** enforce exact plan identity at projection construction; return a detached bounded snapshot, and preserve its identity through serialization. Avoid hashing one mutable object and later copying a potentially changed one. Add a valid positive control, a changed-plan/old-admission rejection, and an alias-isolation test.

### R2 — P1: an any-transport availability requirement receives a false pass

Source: `topology-tools/plugins/validators/security_plan_validator.py:588–611`, `:1013–1023`, `:1077–1099`; related warning decision at `:796–813`.

Availability requirements share `_obligation` with policy overrides. Missing `ports` (also an empty mapping) becomes `ANY_TRANSPORT`. `_check_requirements_are_permitted` iterates `values or ()`, which is empty for this representation. `_required` explicitly skips `ANY_TRANSPORT`. Meanwhile the parsed availability entry is present, so the empty/unattested-Q warning does not fire.

Reproduction: start with the positive fixture authorizing only TCP/53 and declaring that finite requirement; remove `ports` from the requirement, leaving the finite policy unchanged. The real validator returns **errors=0, warnings=0, SEC-AVAIL=pass**. A matching approval then yields **admitted=True**.

This is not the old mistake of deriving availability from permits. It is a distinct requirement which the parser accepts and both checks subsequently omit. Whether an unbounded Q is intended or unsupported, silently discharging it is incorrect.

**Required correction:** give availability requirements an explicit supported grammar separate from override defaults. For the present bounded implementation, reject an unbounded requirement or mark the obligation unverified and block admission. Do not invent an availability promise for every port. Test omitted, null and empty `ports`, alongside supported finite Q and the explicit empty-Q waiver case.

### R3 — P2: keyword detection is not a closed applicability contract

Source: `topology-tools/plugins/validators/strict_admission.py:83–101`, `:164–178`.

Applicability of deferred obligations is inferred by searching serialized plan text for quoted words. There is no corresponding closed schema rejecting every unsupported construct before admission. The comment that a future construct will necessarily trigger refusal is therefore stronger than the implementation.

Reproduction: independently revalidate the same positive plan after adding identical `[{kind: routed}]` metadata under different keys:

| Key | SEC-PATH required | Admission |
| --- | --- | --- |
| `path` | yes | refused |
| `route_through` | yes | refused |
| `paths` | no | admitted |
| `execution_paths` | no | admitted |

This does not establish that these alternative keys have backend semantics today. It establishes that unsupported plan shape passes the purported future fail-closed guard. Absence of a spelling is not independent evidence of non-applicability; unrelated string values can also trigger obligations.

**Required correction:** use a closed, versioned plan shape and typed applicability derived from the supported intent/profile/scope contract. Reject unknown semantic constructs. Keep bounded offline admission distinct from backend qualification; there is no need to implement all deferred F3–F5 work in this fix.

### R4 — P2: approval does not bind the actual waiver statement

Source: `topology-tools/plugins/validators/security_plan_validator.py:206–247`, `:546–558`.

The intent digest includes `availability_attested` only as a set of scope names. Owner and rationale of the waiver are discarded. Changing `{owner: owner-A, rationale: reason-A}` to `{owner: owner-B, rationale: reason-B}`, with Q explicitly empty, leaves the independently computed intent digest unchanged. The previous approval admits the new claim.

The semantic permission set may legitimately be unchanged. The attested statement and responsibility are not unchanged, however, and this is the evidence used to discharge otherwise unverified availability.

**Required correction:** bind the actual waiver/evidence context to approval, possibly through a separate evidence digest rather than polluting the semantic intent hash. Filled strings must not be mistaken for authority. Test that changing the attestation invalidates its approval binding while a semantically unchanged plan may retain its semantic identity.

### R5 — P2: approval epoch is only a label when the plan omits epoch

Source: `topology-tools/plugins/validators/strict_admission.py:293–296`, `:312–318`.

Approval must name an epoch, but equality is conditional on the plan having one. The positive strict fixture has no plan epoch. The same verified plan is admitted with both `old-epoch` and `new-epoch` approvals. No expected epoch is supplied by another trusted input to this API.

This does not prove that an upstream issuer will issue invalid approvals. It shows that the admission boundary itself does not enforce the claimed epoch linkage for this supported input shape.

**Required correction:** require an explicit expected epoch/context for epoch-bound admission and compare it, or clearly scope the present verdict as non-epoch-qualified offline admission. A freshness/revocation implementation is separate work; merely requiring a nonempty string does not implement it.
