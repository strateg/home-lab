## 1. Резюме

**Рекомендуется заимствовать отдельные инженерные механизмы, а не переносить платформы целиком.**

Наибольшую пользу принесут:
1. **Infrahub:** происхождение итоговых значений и анализ последствий изменений.
2. **Kapitan:** чёткая граница между разрешённым inventory и генерацией.
3. **Kratix:** независимые состояния выполнения, готовности и проверки результата.
4. **Nautobot Design Builder:** владение ресурсами и безопасный жизненный цикл удаления.
5. **Commodore / Crossplane:** управляемое обновление переиспользуемых модулей.
6. **Clan:** составные сервисы с ролями на нескольких машинах.
7. **CUE:** переиспользуемые ограничения и производная документация.

Сохраняются Class → Object → Instance, topology как источник истины и lifecycle:

    discover → compile → validate → generate → assemble → build

Предложения не требуют вводить Kubernetes, graph database или ещё один язык конфигурации. Цель — уменьшить количество скрытых решений и исключений, а не увеличить число подсистем.

## 3. Приоритеты

Порядок ниже — рекомендуемая последовательность внедрения, а не severity дефектов. Относительная сложность — предварительная оценка, не оценка в человеко-днях.

| Порядок | Заимствование | Ожидаемый эффект | Сложность |
|---|---|---|---|
| 1 | Field-level provenance / explain | Быстрее понять итоговые значения, меньше ошибок человека и AI | Средняя |
| 2 | Стабильная effective model и projections | Убрать повторное толкование intent в backend | Средняя–высокая |
| 3 | Conditions, привязанные к evidence | Не путать успешную команду с исправной инфраструктурой | Средняя |
| 4 | Ownership / deletion policy | Безопаснее удалять сервисы и общие ресурсы | Высокая |
| 5 | Controlled module upgrades | Предсказуемые изменения общего framework | Средняя–высокая |
| 6 | Составные сервисы | Меньше ручной координации связанных компонентов | Средняя–высокая |
| 7 | Schema-derived tooling / CUE pilot | Согласовать validation, документацию и AI-rules | Средняя |

Объяснение значений можно начать на одном вертикальном сценарии. Массовое распространение provenance следует опирать на стабилизированную effective model.

## 4. Infrahub: происхождение данных и impact analysis

### Что взять

Infrahub хранит инфраструктурные отношения, поддерживает происхождение/владение данными и review изменений. [Обзор Infrahub](https://docs.infrahub.app/overview), [Key Concepts](https://docs.infrahub.app/overview/concepts).

### Адаптация для home-lab

Расширить существующую class lineage до трассировки отдельных итоговых полей:
- source file и путь поля;
- исходное значение или безопасная ссылка на него;
- цепочка defaults и inheritance;
- выполненное преобразование;
- явный instance override;
- итоговое значение;
- ревизия источников.

Пример желаемого объяснения, не существующая команда:

    workload.network.vlan_ref
      object default: @on:host.network.vlan_ref
      host_ref: выбранный host instance
      host default: ссылка на VLAN
      instance override: отсутствует
      result: разрешённая VLAN

Отдельно строить impact analysis по семантическим связям:

    Изменена VLAN:
      затронуты workload network settings
      затронут DHCP
      затронуты firewall policies
      затронут inventory
      требуется повторная генерация соответствующих артефактов

### Ограничения

- Не добавлять graph database: начать с индекса связей в памяти и сериализуемого sidecar.
- Не выводить секретные значения, даже если они участвовали в derivation.
- Отделять provenance от семантического содержимого, чтобы пути workspace и временные метки не ломали determinism.
- Не путать impact analysis с окончательным Terraform plan: это разные уровни анализа.
- Результат должен учитывать не только ссылки, но и групповые политики, capabilities и общие зависимости.

### Приёмка

- Объяснимы explicit override, inherited value и computed value.
- Различаются отсутствие поля, null, false, 0 и пустая коллекция.
- Каждая известная зависимость из fixture попадает в affected set.
- Для секретов отображается только разрешённая metadata.
- Необъяснённое значение помечается как неизвестное происхождение, а не получает выдуманную трассу.

## 5. Kapitan: разрешённый inventory как граница генерации

### Что взять

Kapitan объединяет classes, targets и parameters в inventory, используемый при компиляции конфигурации. [Kapitan Inventory](https://kapitan.dev/latest/pages/inventory/introduction/).

### Адаптация для home-lab

Не заменять компилятор автоматически. Взять принцип явного входного контракта:
1. Источники читаются в предназначенных для этого стадиях.
2. Defaults, references, capabilities и security intent разрешаются единожды.
3. Публикуется версионированная effective model.
4. Validators проверяют её.
5. Generators получают стабильные projections и выполняют backend-specific преобразование.

Snapshot модели должен содержать идентификатор схемы и provenance источников. Зависимости plugins сохраняются явными через depends_on, consumes и produces.

### Ограничения

- Версионировать контракт до подключения множества независимых consumers.
- Не превращать effective model в неограниченную копию всего runtime context.
- Допускать чтение шаблонов и объявленных статических ресурсов; запрещать скрытое повторное толкование исходной topology.
- Неподдерживаемая backend-семантика должна приводить к диагностике, а не молчаливому упрощению.
- Snapshot не должен включать расшифрованные секреты.

### Приёмка

- Генератор работает со snapshot без доступа к исходным topology-файлам.
- При одинаковых snapshot, шаблонах и toolchain получается одинаковое семантическое содержимое.
- Incompatible schema version отклоняется до генерации.
- Независимая перестановка входов не меняет итоговую политику.
- Неизвестная обязательная ссылка не расширяет разрешения.

## 6. Kratix: готовность как набор независимых условий

### Что взять

Kratix разделяет conditions выполнения workflow, доступности и reconciliation; состояния имеют reason и timestamps. [Promise Status and Events](https://docs.kratix.io/main/reference/promises/promise-status-events).

### Адаптация для home-lab

Предлагаемые названия ниже иллюстративные, не утверждённая новая схема:

| Condition | Что подтверждает |
|---|---|
| ModelValid | Конкретная ревизия модели прошла необходимые проверки |
| ArtifactsVerified | Проверен конкретный набор артефактов |
| Applied | Исполнитель завершил применение указанного bundle |
| Healthy | Проверена работоспособность сервиса |
| PolicyVerified | Проверены требуемые ограничения доступа |

Каждое условие связывать с:
- source/model revision;
- bundle digest;
- идентификатором execution;
- observation time и freshness policy;
- reason, evidence reference и областью проверенного поведения.

Хранить изменяемые observations в deploy-state, не менять immutable bundle.

### Ограничения

- Использовать состояния true / false / unknown или эквивалентную явную модель.
- Отсутствие проверки не считать успехом.
- Старое evidence не переносить автоматически на новую ревизию.
- Успешный apply не устанавливает Healthy или PolicyVerified.
- Не требовать PolicyVerified от сервисов, где такая проверка неприменима: это должно определяться контрактом.
- Не превращать наблюдение в автоматический remediation без отдельного решения.

### Приёмка

Негативные сценарии:
- apply успешен, healthcheck провален;
- healthcheck успешен, evidence относится к старому bundle;
- firewall test недоступен;
- deployment завершён частично;
- evidence устарело.

В каждом случае итоговая readiness отражает реальную неопределённость, а не только exit code последней команды.

## 7. Nautobot Design Builder: ownership и безопасное удаление

### Что взять

Design Builder управляет lifecycle инфраструктурных дизайнов, создаваемыми объектами и зависимостями между ними. [Документация Nautobot Design Builder](https://docs.nautobot.com/projects/design-builder/en/latest/).

### Адаптация для home-lab

Описать, кто создал ресурс, кто им управляет и что делать при удалении владельца. Начать с ресурсов, создаваемых одним сервисом, затем рассматривать shared resources.

Пример ожидаемого плана:

| Ресурс | Предлагаемое поведение |
|---|---|
| Выделенный контейнер | Удаление после необходимых проверок и approval |
| Выделенная DNS-запись | Удаление вместе с сервисом |
| Общая VLAN | Сохранение, пока имеются consumers |
| Том с пользовательскими данными | Сохранение по умолчанию |
| Ранее импортированный ресурс | Явное adoption/ownership решение |

### Ограничения

- Исчезновение строки YAML само по себе не является разрешением на destroy.
- Ownership metadata не заменяет Terraform state и механизмы авторизации.
- Правила должны учитывать out-of-band dependencies; неизвестность требует остановки или ручного решения.
- Требуются stable identity, tombstones или эквивалентный способ различать удаление, переименование и потерю источника.
- Не допускать автоматического каскадного удаления persistent data.
- Deletion plan должен учитывать backend-specific ограничения.

### Приёмка

- Общая VLAN сохраняется при удалении одного consumer.
- Persistent volume не удаляется без предусмотренного разрешения.
- Повторная операция идемпотентна.
- Переименование не вызывает необоснованное пересоздание.
- Частичный сбой допускает безопасное повторение или понятное восстановление.

## 8. Commodore и Crossplane: controlled upgrades

### Что взять

Commodore организует reusable components/packages. Crossplane использует revisions композиции и политики их применения. [Commodore Concepts](https://syn.tools/commodore/reference/concepts.html), [Crossplane Composition Revisions](https://docs.crossplane.io/latest/composition/composition-revisions/).

### Адаптация для home-lab

Развивать существующие framework lock и release-процессы:
- связывать проект с проверенной версией framework и зависимостей;
- различать доступную новую версию и разрешённую к применению;
- показывать изменение effective model и артефактов до обновления;
- проверять обновление на тестовом проекте;
- документировать schema/API compatibility, deprecation и миграции;
- сохранять воспроизводимый предыдущий набор входов.

Не вводить независимо от framework lock ещё один несогласованный каталог версий.

### Ограничения

- Откат версии framework не равен откату пользовательских данных или инфраструктуры.
- Backend/provider upgrades могут иметь собственные несовместимости.
- Слишком мелкое версионирование каждого helper увеличит расходы на сопровождение.
- Канареечный прогон на fixture не заменяет проверку на репрезентативном окружении.

### Приёмка

- Новая версия доступна, но проект остаётся на закреплённой версии.
- Несовместимое обновление блокируется заранее.
- Diff показывает изменение effective behavior, а не только текст шаблона.
- Старый артефакт можно воспроизвести при наличии сохранённых зависимостей.
- Известны ограничения rollback для stateful сценария.

## 9. Clan: составной сервис с ролями

### Что взять

Clan Services описывают сервисы с ролями, применяемыми к нескольким машинам. [Introduction to Services](https://clan.lol/docs/25.11/guides/services/introduction-to-services).

### Адаптация для home-lab

Первый кандидат — backup-service:
- source workloads/data assets;
- backup target;
- расписание;
- secret references;
- разрешённые сетевые потоки;
- backup healthcheck;
- restore verification.

Реализовать как композицию существующих классов, объектов, instances и relationships, а не новую независимую иерархию.

### Ограничения и приёмка

- Сервис имеет явные inputs, outputs, dependencies и роли.
- Нет необъявленных cross-plugin reads или ручных исключений в backend.
- Секреты остаются в существующем SOPS/age workflow.
- Перенос backup target меняет согласованный набор ресурсов.
- Проверка восстановления выполняется на согласованной тестовой среде.
- Успешное создание backup не считается доказательством успешного restore.

Переход управляемых устройств на NixOS для этого паттерна не требуется.

## 10. CUE: ограничения и производные инструменты

### Что взять

CUE объединяет данные и ограничения для валидации и конфигурационных преобразований. [CUE Introduction](https://cuelang.org/docs/introduction/).

### Адаптация для home-lab

Главная идея — единый канонический контракт, из которого выводятся:
- validation;
- editor hints;
- справочная документация;
- примеры;
- машинно проверяемые таблицы AI-rules.

Это можно частично реализовать и без CUE, используя действующие JSON Schema и YAML contracts.

### Минимальный эксперимент

Выбрать один небольшой участок схемы, например network attachment. Сравнить текущую реализацию с CUE только на нём:
- понятность ошибок;
- сложность поддержания ограничений;
- совместимость null/false/zero/defaults;
- необходимость конвертеров;
- выигрыш для автора topology.

### Ограничения

- CUE unification не эквивалентна произвольному deep-merge/override.
- Не поддерживать бессрочно две независимые схемы одного контракта.
- Не переносить весь DSL до проверки одного участка.
- Графовые и предметные проверки не исчезают при добавлении schema language.
- Текстовые ADR нельзя без проверки автоматически превращать в достоверные правила.

### Приёмка

Одно изменение канонического ограничения обновляет связанные справочные материалы; несовместимая ручная правка обнаруживается тестом. Политика принятия ADR при этом сохраняется.

## 11. NetBox: использовать как справочник модели или ограниченный источник данных

NetBox полезен как образец network inventory/IPAM/DCIM и API доступа к инфраструктурным данным. [Документация NetBox](https://netboxlabs.com/docs/netbox/).

Для home-lab разумно:
- сверять понятия устройств, интерфейсов, адресов и связей;
- при реальной необходимости добавить read-only import adapter;
- сохранять источник и ownership импортированных полей.

Не рекомендуется внедрять NetBox только ради хранения данных, которые уже удобно сопровождаются в Git. Двусторонняя синхронизация допустима лишь после определения владельца каждого вида данных и правил конфликтов.

## 12. План внедрения

### Итерация A — один объяснимый вертикальный сценарий

Взять существующую связку host → workload → VLAN → service.
- Расширить lineage до нескольких критичных полей.
- Зафиксировать snapshot и projection contract.
- Добавить человекочитаемое объяснение и JSON-формат для инструментов.
- Проверить отсутствие секретов и reproducibility.

**Результат:** оператор понимает итоговые значения без чтения нескольких compiler/generator файлов.

### Итерация B — доказуемая readiness

- Подключить conditions к существующему deploy-state.
- Связать проверки с model revision и bundle digest.
- Пройти сценарии partial failure, stale evidence и unknown checks.

**Результат:** результат команды отделён от подтверждённого состояния сервиса.

### Итерация C — управляемый lifecycle

- Описать ownership одного сервиса и shared dependencies.
- Реализовать план удаления без немедленного выполнения.
- Проверить retain-политику и повторяемость операции.

**Результат:** оператор заранее видит, что будет удалено и что сохранится.

### Итерация D — масштабирование переиспользования

- Проверить controlled upgrade на втором репрезентативном проекте.
- Выделить один составной сервис.
- Провести ограниченный schema-tooling эксперимент, если остаётся измеримая проблема.

**Результат:** новые абстракции добавляются после доказанного выигрыша, а не до него.

## 13. Метрики полезности

До и после экспериментов измерять:
- время поиска причины effective value;
- число файлов, которые пришлось открыть;
- повторяемость ошибок человека/AI на одинаковых задачах;
- число независимых реализаций одной semantic rule;
- долю критичных полей с достоверной provenance;
- корректность affected set на подготовленных fixtures;
- количество случаев, когда success execution ошибочно воспринимался как readiness;
- трудоёмкость переноса сценария на второй проект.

Число токенов полезно как дополнительная метрика, но экономия контекста не должна достигаться ценой потери обязательных правил и проверок.

## 14. Что не заимствовать сейчас

- Kubernetes control plane только ради управления домашней инфраструктурой.
- Graph database без потребности в многопользовательской работе и API.
- Полную миграцию DSL на CUE или Nix.
- Новые runtime stages поверх действующих шести.
- Автоматический cascade delete по исчезновению декларации.
- Непроверенный AI-generated код как основание для apply.
- Исходный код внешних проектов без отдельной проверки лицензии и совместимости зависимостей.

## 15. Процесс принятия и итог

Для каждого принятого изменения:
1. Проверить, какие части уже реализованы в актуальном HEAD.
2. Описать минимальный контракт и ограниченный сценарий.
3. При изменении архитектуры обновить соответствующий ADR и REGISTER; не назначать номера ADR заранее.
4. Обновить применимые rules и tests.
5. Выполнить targeted tests и соответствующие task gates; интеграционную готовность подтверждать отдельно.
6. Не исправлять generated вручную и не изменять устройства вне согласованного deploy workflow.

**Итоговая рекомендация:** начать с объяснимости Infrahub, компиляционной границы Kapitan и conditions Kratix. Затем вводить ownership Nautobot и управляемые обновления Commodore/Crossplane. Остальные паттерны применять только там, где небольшой эксперимент докажет снижение сложности.
