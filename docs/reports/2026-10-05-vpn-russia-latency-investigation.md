# Рапорт: задержки VPN-Russia на Chateau

Дата рапорта: 2026-10-05. Диагностические замеры и захваты: 2026-10-03.
Статус: симптом и повторные передачи подтверждены; первопричина не установлена.
Это сводка проведённых тестов, а не проверка текущего состояния на 2026-10-05.

## 1. Краткий вывод

При подключении ноутбука к AP VPN-Russia HTTPS-запросы выполняются значительно
медленнее, чем через AP VPN-Sweden или российский профиль приложения AmneziaVPN
на том же ноутбуке, подключённом к AP Chateau.

При фиксированном IP назначения медиана запроса через Russia на Chateau —
2,749 с, через Sweden — 0,101 с, через российский профиль приложения — 0,238 с.
В захвате ноутбука видны две серии повторных передач TCP, каждая сопровождается
паузой примерно 1,3 с до получения подтверждения/ответа.

Доказан механизм наблюдаемой задержки на уровне TCP, но не место потери или
задерживания данных/ACK. Не доказана вина сервера, прокси, firewall, MTU или Wi-Fi.

## 2. Условия и ограничения

- Один ноутбук, один домашний провайдер; пользователь переключал AP или профиль приложения.
- Для основной серии: `curl.exe -4 --http1.1`, отдельный процесс на каждый запрос,
  пять повторов с паузой 2 с; HTTPS к `example.com`.
- В решающей серии имя и IP фиксировались через
  `--resolve example.com:443:104.20.23.154`; ответ HTTP 200, HTML 577 байт.
- IP фиксирован, но это не доказывает одинаковый физический узел CDN для разных выходов.
- Приложение может выбирать другой российский endpoint. Его фактический адрес
  не сопоставлен с контейнером; одинаковый сервер пока не подтверждён.
- Тесты измеряют задержки небольшого HTTPS-запроса, а не максимальную
  пропускную способность VPN и не полную браузерную загрузку страницы.
- Замеры последовательные, не одновременные.

## 3. Сравнительные результаты

Значения — медианы пяти попыток. Времена curl накопительные; отдельные этапы
рассчитаны по каждой попытке: TLS = time_appconnect − time_connect;
ожидание HTTP = time_starttransfer − time_appconnect.

| Подключение, фиксированный IP | TCP | TLS после TCP | Полный запрос |
|---|---:|---:|---:|
| AP VPN-Russia, приложение выключено | 84,7 мс | 1338,1 мс | 2749,4 мс |
| AP VPN-Sweden, приложение выключено | 27,9 мс | 39,5 мс | 101,3 мс |
| AP Chateau + приложение Russia | 72,5 мс | 87,1 мс | 238,3 мс |
| AP Chateau + приложение Sweden | 27,8 мс | 42,6 мс | 112,1 мс |

Для AP VPN-Russia медиана ожидания первого байта после TLS — 1327,4 мс;
для AP VPN-Sweden — 33,0 мс. Russia на Chateau примерно в 27 раз медленнее
Sweden и в 11,5 раза медленнее российского профиля приложения по полному времени.

### Предварительные тесты

- `tass.ru`: пользователь наблюдал более медленную браузерную загрузку через Russia.
  Curl получал HTTP 403 и около 1,3 КБ, поэтому его `speed_download` не является
  измерением скорости загрузки сайта. В серии, предполагаемой Sweden, были два
  TCP-таймаута из пяти; порядок этой первоначальной серии явно не подтверждён.
- `example.com` без фиксации IP: Russia использовал `8.47.69.6`, Chateau/Sweden —
  `104.20.23.154`. После фиксации последнего IP задержка Russia сохранилась:
  различие DNS-ответов не объясняет симптом полностью.

## 4. Дополнительные эксперименты

### Принудительный TLS 1.2 через AP VPN-Russia

Полные времена: 2,871; 2,852; 2,911; 4,040; 2,821 с.
Медиана — 2,871 с. Медиана TLS после TCP — 2,688 с; ожидания после TLS — 0,091 с.
Задержка не исчезла, а сместилась внутрь TLS-обмена. Это не подтверждает
специфическую проблему только TLS 1.3.

### MTU 1200 на Wi-Fi ноутбука

Полные времена: 2,741; 2,727; 2,766; 2,951; 2,747 с.
Медиана — 2,747 с: улучшения не видно.

В первом скрипте восстановления допущена ошибка чтения свойства:
`NlMtuBytes` вместо `NlMtu`. Последующая проверка показала Wi-Fi с MTU 1200,
что подтверждает применение уменьшения и отсутствие успешного восстановления.
Пользователю выдана команда установки 1500; подтверждающий вывод после неё
не получен. В последующем захвате исходящий SYN имеет MSS 1460, что согласуется
со стандартным MTU 1500, но не заменяет проверку настройки интерфейса.

Уменьшение MTU ноутбука не устранило симптом. Это ослабляет гипотезу обычного
превышения размера TCP-пакетов, но не исключает все проблемы внешнего AWG-пути.

## 5. Доказательства из захвата пакетов

Файл пользователя: `/mnt/c/Temp/russia.pcapng` (147188 байт при чтении).
Анализ выполнен локально с `tcpdump`; почти одновременные копии одного пакета
на разных точках захвата pktmon исключены из подсчёта повторных передач.

Поток: ноутбук `192.168.57.198:53282` → тестовый сервер TCP/443.

| От первого SYN | Событие |
|---:|---|
| 0,088 с | Получен SYN-ACK |
| 0,097 с | Отправлены 458 байт первых TLS-данных, seq 1:459 |
| 0,420 / 0,745 / 1,357 с | Повторные передачи тех же 458 байт |
| 1,441 с | Пришёл ACK 459 |
| 1,446 с | Пришли данные сервера |
| 1,455 / 1,458 с | Отправлены следующие 80 и 97 байт |
| 1,785 / 2,107 / 2,707 с | Повторные передачи объединённых 177 байт, seq 459:636 |
| 2,799 с | Пришли данные сервера и ACK 636 |

Повторяются небольшие сегменты, не только полноразмерные. Клиентский захват
не различает потерю исходящих данных, потерю обратных подтверждений и задержку
их обработки. Входящий агрегированный блок 4080 байт нельзя трактовать как
доказательство такого размера пакета на проводе: возможна агрегация в стеке.

## 6. Проверенное состояние Chateau во время диагностики

- RouterOS 7.24.5; в доступных снимках обоих сеансов CPU не превышал 6%.
  Во время разрывов мониторинга нагрузка неизвестна.
- Оба AWG WireGuard-интерфейса running; MTU 1420.
- Оба контейнера privileged=true.
- Sweden: образ с тегом `1.4.0`; Russia: `latest`.
  По тегам нельзя заключить, что запущенные бинарники различаются:
  фактическая версия/digest Russia не установлены.
- Действующее MSS-правило Russia с new-mss=1360 имеет ненулевой счётчик.
  Присутствуют дубли и старые правила с потерянными ссылками на интерфейсы;
  причинная связь с задержкой не доказана.
- Присутствует общий FastTrack. Его применимость к конкретному тестовому
  соединению и порядок исключений ещё не исследованы полностью.
- В topology у Russia есть дополнительные параметры padding/rekey.
  Документация проекта указывает, что CONTENT_PADDING и соответствующие
  дополнительные таймеры принимаются, но игнорируются прокси. Утверждать,
  что они создают задержку, оснований нет; соответствие документации конкретному
  запущенному бинарнику ещё нужно проверить.

Мониторинг через REST терял доступ к Chateau во время подключения ноутбука к
обоим VPN-AP. Поэтому объёмы 4,41 МБ для Russia и 3,22 МБ для Sweden за окна
сбора не являются сопоставимым speedtest или точными замерами загрузки сайта.

## 7. Препятствие захвату на роутере

Первый запуск sniffer с automation-credentials отклонён из-за отсутствия прав.
После использования admin из SOPS-секрета устройства обнаружен другой запрет:
`failure: not allowed by device-mode`.

Проверено: mode=home, sniffer=false. После неудачных запусков настройки sniffer
восстановлены, sniffer остановлен. Права пользователей не менялись.

Отправка последующей команды device-mode/update с sniffer=yes прервана.
Её выполнение и текущее состояние не подтверждены. Перед новой попыткой
необходимо снова прочитать device-mode. Пользователю рекомендовано не нажимать
Reset и не отключать питание без подтверждённого окна активации.

Включение sniffer требует физического подтверждения и вызывает перезагрузку.
Сам захват может изменить работу FastPath/FastTrack: исчезновение симптома
при включённом sniffer необходимо фиксировать как отдельный результат.

## 8. Рабочие гипотезы

1. Потеря/задерживание данных или ACK на российском пути — соответствует захвату,
   но не локализовано.
2. Особенность Russia-прокси: сборка, UDP offload/GSO или обработка пакетов —
   требует A/B на одном endpoint и одной сборке.
3. Firewall/FastTrack/policy routing на Chateau — требует проверки конкретного потока.
4. Другой endpoint в приложении — остаётся важным фактором сравнения.
5. MTU/фрагментация — не подтверждены; тест MTU 1200 не помог.

Ключи и авторизация не являются основной текущей гипотезой: handshake проходит,
HTTP 200 и полезные данные получены. Смена ключей не обоснована.

## 9. План продолжения

1. Подключить отдельное SailfishOS-устройство к AP VPN-Russia; ноутбук оставить
   на Chateau для непрерывного доступа управления. Терминал/SSH пользователь
   подтвердил; IP, SSH-пользователь и наличие curl/tcpdump пока не предоставлены.
2. Проверить MTU клиента, отключение VPN-приложения и повторить фиксированный
   HTTPS-запрос. Это отделит особенности Windows от общего российского пути.
3. Сопоставить фактический endpoint приложения с endpoint контейнера.
4. Проверить текущий device-mode; при необходимости согласованно разрешить
   sniffer с физическим подтверждением и перерывом связи.
5. Снять синхронные ограниченные захваты: клиентский TCP, участок до прокси
   и внешние UDP. Установить, где появляются пропуски и паузы.
6. Проверить версию бинарника, статистику дропов прокси и релевантные firewall
   счётчики. Затем A/B одного фактора: например, GSO включён/выключен, если
   установленная версия поддерживает параметр.
7. Все постоянные инфраструктурные изменения выполнять через topology →
   compile → generate → plan → apply; сохранять исходные значения и откат.
   Sweden оставить контрольным работающим туннелем.
8. После устранения задержек отдельно измерить пропускную способность загрузкой
   достаточно большого объекта с одинаковыми условиями и несколькими повторами.
